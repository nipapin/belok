# Роли сотрудников

## Совместимость

Исходные `users.role = USER / ADMIN` не изменяются при выпуске обновления и при назначении новых рабочих ролей. Без ручного назначения сохраняется исходный доступ. Все существующие сессии остаются действительными.

Назначение хранится отдельно в существующей таблице `app_settings`, ключ `employee_roles:<userId>`. Назначенные роли **заменяют**, а не дополняют исходные права. Например, исходный ADMIN + назначенный COOK имеет только права повара. Это также учитывают клиентские API заказов, PIN-доступ кассы и отправка служебных push-уведомлений. Проверки используют актуальное назначение из БД на каждом запросе.

Новые миграции, изменение enum и автоматическое переназначение аккаунтов не нужны. Пользователь сам выбирает роли в «Пользователи» или «Сотрудники» → «Изменить». После назначения рабочей роли клиент появляется в сотрудниках. «Сохранить исходный доступ» возвращает прежнее поведение. «Клиент» явно снимает рабочий доступ, в том числе у исходного ADMIN.

## Доступ

| Роль | Доступ |
| --- | --- |
| Владелец | Все существующие разделы и назначение любых ролей |
| Управляющий | Меню, отчётность, заказы, касса, склад, стоп-лист; назначение операционных ролей |
| Кассир | Заказы, касса и лояльность, кухонная доска; отмена только неоплаченного незавершённого заказа |
| Повар | Кухонная доска до статуса «Готов», просмотр кухонных техкарт, стоп-лист; без денежных сумм на доске |
| Кладовщик | Просмотр склада и рецептур, движения, приход, списание, инвентаризация, выпуск партии; без редактирования каталога и рецептур |
| Клиент | Клиентская часть и собственные заказы |

Операционные роли можно совмещать. Клиент не совмещается с рабочими ролями. Неизвестные роли не дают прав. Управляющий не назначает владельца/управляющего, не изменяет привилегированные аккаунты и не восстанавливает исходный ADMIN. Владелец может назначить себе OWNER; снять у себя административный доступ нельзя. Роли других сотрудников можно ограничивать вручную.

Существующие отдельные складские права ADMIN (`inventory_access`) сохраняются. Для новых рабочих ролей действует общая матрица, старые складские назначения не могут вернуть права повару.

## Журнал

Ручное назначение/снятие ролей и изменение стоп-листа фиксируются вместе с изменением в одной транзакции. Журнал доступен владельцу, исходному администратору и управляющему в «Журнал доступа». Ключи `staff_audit:<uuid>` содержат автора, объект, время, старое и новое значение; экран показывает последние 200 событий. Существующий журнал складских операций остаётся отдельным.

Этот выпуск разграничивает функции, которые уже есть в приложении. Мультизаведения, управление сменами, передача владения, удаление заведения и общий аудит всех финансовых действий требуют собственных моделей и не создаются этим изменением.

## Проверка

`npm run test:roles` проверяет разрешения, совмещение, запрет повышения прав, серверный отказ при удалении товара поваром, ручное назначение в изолированной PostgreSQL-совместимой БД, сохранность USER/ADMIN, защиту своего доступа, кухонную выдачу и запрет кассиру вернуть оплаченную покупку. `INVENTORY_TEST_PGLITE_MODULE` должен указывать на тестовый PGlite. Тест включён в production Actions.
