# Варианты и добавки товаров

Реализация находится в ветке `dev`. Исходная задача и расшифровка голосовых сообщений: [task-product-options-2026-10-08.md](task-product-options-2026-10-08.md) и [transcript-2026-10-08.md](transcript-2026-10-08.md).

## Настройка в админке

У каждого варианта можно задать цену, объём в мл, вес в граммах, калории, белки, жиры, углеводы и клетчатку. Пустое поле наследует значение товара, а `0` означает именно нулевое значение. Варианты остаются в одной карточке меню и киоска; стрелки и горизонтальное листание меняют выбранный вариант.

Для ингредиента доступны признаки «В составе», «Можно убрать» и «Добавка». Пустая группа означает независимую добавку: например, протеин, сыр или халапеньо.

Одинаковое название группы объединяет ингредиенты в один выбор. Например, для группы «Молоко»:

- Обычное молоко: «В составе» и «Можно убрать», без признака «Добавка».
- Овсяное и соевое молоко: «Добавка», без признака «В составе».

В группе допускается один исходный ингредиент. При выборе альтернативного молока исходное автоматически удаляется из состава. Цена альтернативы служит доплатой к цене напитка. Группу без исходного ингредиента можно использовать для сиропов; первым пунктом будет «Без добавки».

Цены ингредиентов задаются в разделе ингредиентов. Реальные цены, размеры, КБЖУ и доступность добавок нужно заполнить по действующему меню; тестовые товары не загружаются в рабочую базу. КБЖУ отражают выбранный вариант товара: расчёт питательности добавок в эту задачу не входил.

## Заказы

Обычный заказ и киоск используют общий серверный расчёт цены варианта и доплат. Сервер проверяет наличие товара, принадлежность варианта и ингредиентов, доступность добавок, количество и единственный выбор в группе. Переданная клиентом доплата не используется при расчёте.

В заказе сохраняются название варианта, названия добавок и их доплаты на момент оформления. Редактирование ингредиента после заказа не меняет эти значения. Разные варианты и наборы добавок образуют разные строки корзины.

## База и запуск

Для запуска этой версии на окружении разработки необходимы миграции `018_product_spiciness.sql` и `019_product_options.sql` через существующий механизм `npm run db:migrate`. Перед запуском укажите `DATABASE_URL` базы разработки. Применение миграций к рабочей базе и развёртывание в рамках этой работы не выполнялись.

Ветка `dev` изначально не содержала реализации перчиков. В неё перенесён отдельный коммит с полем остроты, сохранением в админке и индикаторами уровней 0–3.

## Проверки

```sh
npm run test:product-options
npm run test:product-options:integration
npx tsc --noEmit
```

Интеграционный тест требует локальный PostgreSQL. `TEST_DATABASE_URL` может задавать локальную базу явно; без него используются реквизиты `DATABASE_URL` с заменой адреса на `127.0.0.1`. Внешние адреса запрещены тестом. Все таблицы создаются в отдельной временной схеме, которая удаляется по завершении. Тестовый сервер работает на порту 3310 с отдельным каталогом `.next-test`; внешние платежи и уведомления отключены.

Проверяются реальные API админки и двух типов заказов, подмена цен, недопустимые опции, совместимость старых товаров, снимки названий, интерфейсы меню и киоска на ширинах 390 и 1440, переключение вариантов, выбор добавок, корзина и сохранение формы админки. Снимки экрана и журнал сервера находятся локально в `output/product-options-qa`.

Полный ESLint на текущей ветке содержит ранее существовавшие ошибки в других компонентах; изменённые файлы проверяются отдельно. Доставка наборов еды на день остаётся отдельной задачей: в голосовых сообщениях не определены состав наборов и правила заказа.
