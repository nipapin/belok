# Рабочее пространство управляющего

Локальная реализация от 11 октября 2026. Публикация на сервер не выполнялась, рабочая БД не изменялась.

- `/admin/manager`: ссылки на отчетность, склад, ТТК и заказы; текущие складские показатели; доступность меню и причины стопа. Обновление каждые 10 секунд.
- `/admin/reports`: произвольные даты включительно, быстрые периоды до двух лет, поиск блюда/варианта, тип оплаты и включение отмененных заказов. Видны блюдо, количество, сумма позиции и заказа, дата/время, оплата, статус и комментарий. Серверная пагинация по 50 позиций; CSV всего периода до 100 000 позиций. При большей выгрузке API просит уменьшить период, не обрезает результат молча.
- `/admin/recipes`: отдельный пункт «Техкарты» в меню; список всех блюд и активных заготовок, поиск, фильтр типа и незаполненных ТТК. Открытие и сохранение через существующий редактор. Ссылка также доступна со склада.

## Правила расчета

Отчет считает календарные дни в Калининграде. Сумма каждого заказа учитывается один раз. При поиске блюда сумма относится к целым заказам, содержащим блюдо, количество — к найденным позициям. Отмененные заказы по умолчанию исключены. Исторические цены берутся из заказа, названия блюд — из текущего каталога (отдельного снимка названия блюда существующая схема не хранит).

Стоп-лист рассчитывается на запросе по остаткам и нормам ТТК. Для выхода в шт. норма делится на выход; для выхода в г. используется масса блюда. Для выхода в мл. без нормы порции расчет недоступен. Покупной товар использует складскую привязку вместо ранее заполненной рецептуры. Готовая заготовка расходуется из своего остатка, наличие сырья не считается готовой продукцией. Архивированный компонент ставит блюдо на стоп. Для комбо проверяется достаточное число доступных вариантов в обязательных группах.

Гостевые карточки показывают «На стопе» и блокируют добавление. Меню и карточки обновляются каждые 10 секунд, киоск — каждые 5 секунд. Сервер при оформлении проверяет общий расход по всем позициям заказа и выбранному составу комбо, включая общий ингредиент у разных блюд.

Доступность не заменяет резервирование и списание. Эти операции пока не подключены: параллельные заказы могут пройти проверку одного остатка до его изменения персоналом. Варианты используют общую ТТК блюда; складские нормы добавок отдельно не связаны с ингредиентами меню. Для полной автоматизации нужны сохраненный состав заказа, нормы вариантов/добавок и транзакционный резерв/списание.

Блюда без ТТК/привязки остаются под ручным управлением и отображаются управляющему «Без расчета». На установке без складских таблиц сохраняется ручная доступность. Ошибки подключенной БД не маскируются отсутствием ТТК. Права склада и аудит существующих операций сохранены.

## Проверка

- `npm run test:manager`: границы дат, CSV, точность норм, нехватка, архивирование и суммарный расход корзины.
- `npm run test:manager:integration`: фактический SQL обработчиков отчетов, списка ТТК и доступности на изолированной PostgreSQL/PGlite. Требует `INVENTORY_TEST_PGLITE_MODULE`; не использует `DATABASE_URL`.
- `npm run test:manager:browser`: локальный сервер, все API подменены. Проверяет открытие/сохранение ТТК, двухлетний период, пагинацию, ширину 1440/390 px и обновление гостевого стоп-листа. Снимки сохраняются во временный каталог `belok-manager-preview`.
- Проверены TypeScript, ESLint измененного кода, существующие тесты склада, панели и опций товаров.
