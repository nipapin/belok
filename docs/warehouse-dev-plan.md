# План склада для dev

Дата: 11 октября 2026. Работаем локально. Основа — присланный владельцем роадмап.

## Цель ближайшего цикла

Получить проверяемый внутренний учёт: начальный остаток → приход → выпуск заготовки → списание/потери → инвентаризация. Подключать автоматическое списание заказов только после приёмки этого цикла.

## Что подтверждено в коде

- Сырьё, покупная продукция, заготовки и упаковка; единицы g, ml, pcs; остатки и минимумы. Для покупной продукции нужна новая миграция.
- Карточка создаётся с нулём. Начальный остаток, приход, списание и инвентаризация проводятся отдельными операциями с причиной, автором и ключом защиты от повтора.
- Есть рецептуры блюд и заготовок, привязка покупного товара, API выпуска партии.
- Выпуск партии блокирует затронутые остатки, списывает компоненты и приходует заготовку в одной транзакции.
- Есть журнал движений, аудит и складские права.
- Связь продаж со складом выключена. Наличие кода и SQL-файлов не подтверждает применение миграций или правильность реальных остатков.

Перед изменением схемы подготовить резервную копию. | Известна БД, проверен доступ, есть безопасный набор тестовых позиций. Проверка не меняет реальные остатки. |

| 4. Техкарты и производство | Проверить одну заготовку и одно блюдо: состав, нормы, выход и потери. При выпуске партии сохранить использованную версию/снимок рецептуры и фактический выход. Добавить защиту от повторного выпуска, проверить вложенные заготовки. | Компоненты списаны один раз, готовая заготовка оприходована. Изменение рецепта не меняет историю партии. |

Затем варианты, добавки, комбо и доступность меню. | Последний компонент нельзя зарезервировать дважды; повтор события не создаёт второе списание. Возврат денег не возвращает продукты автоматически. |

## Что исправить/проверить первым

1. Исправлено: количество показывается без обрезания дробной части. Для g/ml допустимы до трёх знаков, для pcs — целые значения. Приход и списание считаются в тысячных долях без ошибок двоичной арифметики.
2. Исправлено: старый PATCH отключён; операции идут через отдельный API. Инвентаризация сравнивает остаток с тем, который пользователь видел при открытии формы.
3. API партий выполняет транзакцию, но повторный запрос не защищён отдельным ключом операции. Предусмотреть защиту от повторного проведения до реальной работы.
4. Историю изменений рецепта нельзя считать снимком состава партии. Проверить сохранение состава и норм на момент выпуска.

## Контрольный пример

В изолированных тестовых данных: сырьё 1000 г → приход 500 г → выпуск 4 порций заготовки с расходом 100 г сырья на порцию → потеря 50 г сырья → инвентаризация сырья с фактом 1040 г.

Ожидаемо: сырьё 1040 г, заготовка 4 шт.; журнал содержит +1000 OPENING, +500 RECEIPT, −400 PRODUCTION_INPUT, −50 WRITE_OFF и −10 RECOUNT. Повтор проведения партии не меняет количества. Список компонентов партии остаётся прежним после редактирования рецепта.

Подготовить отдельную локальную dev-БД с текущей складской схемой и применить `zz_inventory_stock_operations.sql`. Затем внести 5–10 контрольных позиций и пройти цикл приёмки. Следующий этап кода — защита выпуска партии от повтора и сохранение снимка рецептуры.

## Реализовано локально 11 октября

- Четыре типа позиций, карточка без поля изменения остатка, примечание и минимум пополнения.
- После создания карточки открывается внесение начального остатка; форму можно закрыть и внести количество позже.
- Отдельные приход, списание и инвентаризация; просмотр последних 100 движений с причиной, датой, автором и остатком после операции.
- Начальный остаток разрешён только без предыдущих движений. Приход заготовки направляется в производство; начальный ввод существующей заготовки разрешён.
- Операция выполняется одной транзакцией и блокирует строку остатка. Повтор с тем же ключом и данными возвращает предыдущий результат; изменённые данные с тем же ключом отклоняются.
- Исправлена проверка количества в API выпуска партии и привязки покупного товара, которая ранее отклоняла обычные положительные значения.

Проверки: тест точности и пределов; изолированный PostgreSQL через PGlite с реальными складскими миграциями, операциями и триггерами аудита; интерфейс в Edge на 1440 и 390 px с подменёнными API. Проверены повтор, нехватка, устаревшая инвентаризация, откат ошибочных операций, автор движений и создание карточки → начальный остаток. Многопользовательская нагрузка на отдельном PostgreSQL остаётся частью приёмки.

Миграция на подключённой рабочей БД не запускалась. Публикация кода в dev не применяет миграции автоматически.
